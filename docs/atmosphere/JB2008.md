# JB2008 — external official Fortran backend

Direct-reference Jacchia–Bowman 2008 thermosphere baseline for `leo-dynamics`.

Nothing of the model is reimplemented. The backend evaluates the official
Space Environment Technologies Fortran source unmodified, compiled in place, and
exposes it through a project-owned ISO C binding. There is no caching, no
interpolation of model results, no surrogate and no fallback: every requested
density comes from a full evaluation of `JB2008`.

`cmake/jb2008.cmake` calls `enable_language(Fortran)`, so the compiler is chosen

On Ubuntu 24.04 the arch-prefixed driver lives in `gfortran-13-x86-64-linux-gnu`
and `/usr/bin/gfortran-13` is only a symlink to it, so that package is required
as well as the metapackage. Validated with `GNU Fortran
(Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0`: from a clean prefix, a fixed-form F77
subroutine and program compiled with `-std=legacy`, linked, and produced the
correct result.

The driver itself runs with no environment setup. Binaries it produces do need
`libgfortran.so.5` unless the Fortran runtime is linked statically; either

* compile and link with `-static-libgfortran` (verified: the resulting binary has
  no `libgfortran` dependency), or
* run with `LD_LIBRARY_PATH=/tmp/leo-fortran/usr/lib/x86_64-linux-gnu`.

## 3. Fortran ABI and the project bridge

`JB2008.f` is fixed-form Fortran 77 with `IMPLICIT REAL*8(A-H,O-Z)` and
`IMPLICIT INTEGER*4(I-N)`. It is compiled with `-std=legacy` and
`Fortran_FORMAT FIXED`; changing either changes semantics, so both are set
explicitly on the source file.

All real arguments are `REAL*8` (IEEE binary64) and all dummy arguments are
passed by reference. The project-owned bridge
`src/atmosphere/jb2008_bridge.f90` declares them as `real(c_double)` through
`ISO_C_BINDING` and exports

```fortran
subroutine leo_jb2008(mjd, sun, sat, f10, f10b, s10, s10b, m10, m10b, &
                      y10, y10b, dtc, temp, rho) bind(C, name="leo_jb2008")
```

so the C++ side sees plain `double` pointers with no hidden length arguments
(the reference is only called by the bridge, which has no `CHARACTER` dummy
arguments, so no inter-argument length is appended).

**Double-precision ABI enforcement.** Every value crossing the boundary is
`real(c_double)`. The C++ adapter additionally validates that every input is
finite and inside the documented domain *before* the call, and rejects
non-finite or non-positive results afterwards, so a hypothetical
single-precision or mis-marshalled build fails loudly instead of returning
plausible numbers.

**Returned semantics.**

| Fortran output | Meaning | C++ field |
|---|---|---|
| `TEMP(1)` | Exospheric temperature above the input position, `Tsubl + DSTDTC`, K | `exospheric_temperature_k` |
| `TEMP(2)` | Temperature at the input position, K | `temperature_k` |
| `RHO` | Total mass density, kg/m³ | `density_kg_m3` |

Note that the published expected-output files label `TEMP(1)` as `TINF`. That
label is inaccurate: the driver's internal `TINF` additionally carries the
local-solar-time/latitude correction `DTCLST` and is never written out. What
appears in the file is `TSUBL + DSTDTC`, i.e. `TEMP(1)`.

### 3.1 Reentrancy and thread policy

`JB2008` itself holds **no** `COMMON`, `SAVE` or module state: every quantity is
a dummy argument or a local `DATA` constant, so the Fortran routine is
reentrant and there is no initialisation step. The operational driver
(`JB08DRVAUTO.f`) is the opposite — it caches whole index files in `COMMON`
blocks `/CSOLFSMY/` and `/DTCDATA/` — but none of that code is linked into this
backend.

Nevertheless `leo::atmosphere::Jb2008::evaluate` serialises the call behind a
process-wide mutex. The official read-me warns that the model may raise
`IEEE_UNDERFLOW_FLAG`/`IEEE_DENORMAL` at high altitude; if the Fortran runtime is
ever configured to trap floating-point exceptions, concurrent evaluation would
make such a signal non-deterministic. Serialisation costs nothing in the
single-threaded propagation case and keeps the thread-safety statement simple
and true: **the backend is thread-safe only in the sense that concurrent callers
are serialised; evaluation is never parallelised inside the library.**

## 4. Model input contract

These are the exact conventions of the reference implementation. They are *not*
NRLMSISE-00 conventions.

### 4.1 Time base

| Quantity | Definition |
|---|---|
| `D1950` | Days since 1950 Jan 0.0 (= 1949 Dec 31, 00:00 UT), fractional |
| `AMJD` | Modified Julian Date, `AMJD = D1950 + 33281.0`, i.e. `JD − 2400000.5` |
| Semiannual phase | `CAPPHI = DMOD((AMJD − 36204.0)/365.2422, 1.0)` |
| Semiannual day of year | `TMOUTD(AMJD − 33281.0)` → day of year with fraction |

`AMJD` is used only for the semiannual term and the seasonal-latitudinal term;
nothing else in the model depends on the epoch.

### 4.2 Solar index lags (exact, from the reference driver)

`SOLFSMY` is queried with the request time shifted backwards by whole days, and
the record index is truncated, so for any time inside a day the index used is
the record of the **previous calendar day**:

| Index | Lag | Reading |
|---|---|---|
| `F10`, `F10B` | 1 day | record of day `d − 1` |
| `S10`, `S10B` | 1 day | record of day `d − 1` |
| `M10`, `M10B` | 2 days | record of day `d − 2` |
| `Y10`, `Y10B` | 5 days | record of day `d − 5` |

The `…B` values are the **81-day centred averages published in the same
record**, not an average recomputed from the daily series. In other words the
averages are lagged exactly like their daily counterparts. All indices are
dimensionless and already scaled to F10 units.

The reference driver also substitutes **zero** for any daily/average pair whose
members fall below 40, and then skips the whole request, retrying at the next
input record. This project does not reproduce that substitution: out-of-domain
indices are rejected (`std::invalid_argument`) rather than silently zeroed.

### 4.3 Geomagnetic storm term (`DSTDTC`)

`DTCMAKEDR_AUTO.f` builds an hourly `DSTDTC` series from the 1-hourly Dst index.
`DTCVAL` then, for a request time:

1. forms `FX = 1 + (T1950 − DT1950 + 1e−8)·24` (hours since the first record);
2. **linearly interpolates between the two bracketing hourly values**;
3. adds `0.5` and assigns to `INTEGER*4`, i.e. the result is rounded to the
   nearest whole kelvin by truncation;
4. aborts if the request lies outside the loaded range or if the file has a gap
   (`IDTCH > 2000` or `DT > 1.01/24`).

`DSTDTC` is a temperature increment in kelvin added to the exospheric
temperature (`TEMP(1) = TSUBL + DSTDTC`, and `TINF = TSUBC(1+0.31·DF) + DSTDTC +
DTCLST`). It is **not** a density correction.

This hourly interpolation is an interpolation of an *input index series*, not of
atmospheric results. It is performed by the caller (the weather-data layer),
never inside the atmosphere evaluation, and the evaluated density is always the
full model evaluation at the requested epoch.

### 4.4 Coordinates

| Input | Meaning |
|---|---|
| `SUN(1)` | Solar right ascension, radians |
| `SUN(2)` | Solar declination, radians |
| `SAT(1)` | Right ascension of the evaluation point, radians |
| `SAT(2)` | **Geocentric** latitude, radians |
| `SAT(3)` | Height, km — see below |

The driver forms `SAT(1) = DMOD(GWRAS + XLON·π/180 + 2π, 2π)` where `GWRAS` is
the right ascension of the Greenwich meridian and `XLON` is **east longitude in
degrees**. Latitude is used geocentrically with no geodetic conversion anywhere
in the model.

The model only ever uses `SAT(1) − SUN(1)`, `SAT(2)` and `SAT(3)`, so supplying
both right ascensions in any single consistent inertial frame gives the same
hour angle. **Basis mixing is forbidden**: `SUN(1)` must not be referred to the
mean equinox of date while `SAT(1)` is referred to J2000/ITRF, or vice versa.

**Height.** `SAT(3)` feeds `XAMBAR`, the gravity term `9.80665/(1 + Z/6356.766)²`
and the layer integration of the barometric/diffusion solution. The distributed
source does **not** state an altitude datum, and the 6356.766 km appearing in
the gravity term is an effective-gravity fit constant of the empirical model, not
a declaration of the reference ellipsoid (it is not the WGS-84 semi-major axis,
6378.137 km). The driver passes its grid altitude through untouched, so the
fixture gives no evidence about the datum either.

Consequently this project applies its documented engineering convention — the
ellipsoidal (geodetic) altitude produced by the common coordinate layer — the
project engineering convention recorded in `docs/atmosphere/DECISIONS.md` — and
records that as a project choice, not as a model requirement. See JB-D05 for the
open question.

### 4.5 Solar and sidereal conventions of the reference driver

`SUNPOS` is the low-precision *Astronomical Almanac* C24 solar position
(accurate to 0.01° over 1950–2050) referred to the **mean ecliptic and equinox
of date**, without aberration or nutation. `THETA` is Greenwich mean sidereal
time referred to the mean equinox of date, evaluated directly from the UTC
argument with no UT1 correction.

*Earth rotation.* Because `THETA` is driven by UTC, the driver implicitly treats
UT1 as UTC. For the validation epoch (2023) |DUT1| stayed below 0.9 s, which is
at most 6.6e−5 rad of hour angle. The 37 s figure frequently quoted alongside
this model is **TAI−UTC**, not UT1−UTC, and does not apply to the sidereal
argument. No test asserts a numeric impact of the Earth-rotation convention; the
reproducibility statement is that both the fixture path and the propagation path
use UTC as the sidereal argument, while the propagation path obtains the actual
Earth rotation angle from SPICE Earth-orientation kernels.

`FZZ = FZM(1) + FZM(2)·FSMB + FZM(3)·FSMB·HTZ + FZM(4)·FSMB·HTZ² + FZM(5)·FSMB²·HTZ`
with `FSMB = F10B − 0.70·S10B − 0.04·M10B` and `HTZ = Z/1000`.

`GTZ` is the constant term plus the first two harmonics of `τ = (DAY−1)/365`
mixed with `FSMB = F10B − 0.75·S10B − 0.37·M10B`.

`FZZ` is floored at `1e−6`. The caller applies `DLRSA = 0` when `FZZ < 0`
before that flooring, a branch the reference reaches only outside its published
fit domain.

## 6. Accepted domain and rejection policy

`Jb2008::evaluate` rejects with `std::invalid_argument` unless all hold:

| Input | Accepted | Rationale |
|---|---|---|
| all 14 scalars finite | required | NaN/Inf cannot be integrated |
| `SAT(3)` height | 120 … 1500 km | published validation grid; `DTSUB` is zero outside 120–800 km and the low-altitude layers start at 90 km, so extrapolating outside the delivered regime is not a supported use |
| `|SAT(2)|` | ≤ π/2 | geocentric latitude |
| `|SUN(2)|` | ≤ π/2 | solar declination |
| `AMJD` | ≥ 0 | |
| `F10`, `F10B`, `S10`, `S10B`, `M10`, `M10B`, `Y10`, `Y10B` | ≥ 40 | the reference driver treats values below 40 as missing; this project fails instead of substituting zero |
| `DSTDTC` | 0 … 2000 K | physical range of the Dst-derived increment; the reference aborts on `> 2000` |

Right ascensions are wrapped into `[0, 2π)`, so any equivalent unwrapped value is
accepted.

## 7. Validation

Two independent oracles are used. The **primary** one is a set of full-precision
reference densities, because it is the only oracle whose inputs are not rounded.
The official SET grid is retained as a **secondary** structural check: it spans a
far larger region and a much wider range of storm conditions, but its printed
inputs limit what any implementation can be expected to reproduce.

### 7.1 Primary oracle — twelve full-precision reference densities

`tests/jb2008_tests.cpp`, `kLegacyReferences`, test case
*"JB2008 reproduces twelve full-precision independent reference densities"*.

Twelve rows of full-precision inputs and reference densities, taken from
`LegacyInputParams` / `checkLegacy.rhoRef` in
`src/test/java/org/orekit/models/earth/atmosphere/JB2008Test.java` at Orekit
commit `6fdf97c133c1ab8c56d7608688419bf4becacf80` (Apache-2.0), fetched and
parsed outside this repository. Each row carries MJD(UTC), solar RA and
declination, spacecraft RA and geocentric latitude, native height in km, the
eight solar indices and `DSTDTC`, and a reference density — all at full printed
precision.

Coverage: MJD 53316.0045 – 53321.5056, heights 373.45 – 398.91 km, geocentric
latitudes −0.9063 – +1.2978 rad, `DSTDTC` 3 – 327 K, and four distinct
quiet-to-active index sets. It is therefore a spread of solar and geomagnetic
conditions rather than a single epoch, but it is a narrow slice of altitude and
latitude compared with the official grid.

*Provenance limitation:* that file names no Fortran driver for these rows, so
their upstream origin is undocumented. They are an independent published
reference, but their generating implementation is unidentified.

**Measured result** (parent run: gcc Release, official `JB2008.f`,
`LEO_JB2008_VALIDATION_DIR=/tmp/leo-atmosphere-deps/jb-validation`; stdout line
`{"model":"jb2008","full_precision_fixtures":12,"max_relative_error":1.4717105248216975e-05}`):

| Quantity | Value |
|---|---|
| Fixtures | 12 |
| Max relative density error | **1.4717105248216975e−05** |
| Inherited upstream tolerance | 2e−5 |
| Margin | 26 % below the inherited tolerance |

The 2e−5 tolerance is **inherited from the upstream test**, not fitted to this
implementation; it is an externally supplied acceptance bound, which is what
makes it meaningful as an oracle. This result is final and supersedes the
previous provisional status.

### 7.2 Secondary oracle — official SET validation grid

Test case *"JB2008 reproduces the official SET validation epochs"*.

The SET validation archive publishes eight three-hourly epochs of 2023 DOY 91
(2023-04-01) at 00, 03, 06, 09, 12, 15, 18 and 21 UT, each with 68191 rows on
a 97 × 37 × 19 grid: altitude 120–600 km in 5 km steps, east longitude 0–360°
in 10° steps, geocentric latitude −90…+90° in 10° steps, ordered latitude
outermost, then longitude, then altitude. Every row carries `Z, LON, LAT,
TEMP(1), TEMP(2), RHO`. Provenance is recorded in §2.1 and checked at run time.

All eight epochs share one solar index set (`F10 = 129`, `F10B = 152`,
`S10 = S10B = 120`, `M10 = 172`, `M10B = 170`, `Y10 = 170`, `Y10B = 165`) and
span `DSTDTC ∈ {24, 50, 85, 115}`, so the storm term is exercised from quiet to
strongly disturbed, including a non-monotone sequence.

The test samples every 41st row plus both endpoints of each file (41 is coprime
with 97, 37 and 19), 1666 rows per epoch, **13328 evaluations in total**.

**Measured result** (same parent run as §7.1: gcc Release, official unmodified
`JB2008.f`, `LEO_JB2008_VALIDATION_DIR=/tmp/leo-atmosphere-deps/jb-validation`;
stdout line
`{"model":"jb2008","fixtures":13328,"max_density_relative_error":0.0058605859224980525,"rms_density_relative_error":0.0032388564212367911,"max_exospheric_temperature_error_k":0.75016676289965289,"max_local_temperature_error_k":0.74605275498265655}`):

| Quantity | Measured |
|---|---|
| Samples | 13328 |
| Max relative density error | 5.8605859224980525e−03 |
| RMS relative density error | 3.2388564212367911e−03 |
| Max exospheric temperature error | 0.75016676289965289 K |
| Max local temperature error | 0.74605275498265655 K |

The full-precision fixtures of §7.1 agree 398× better on the same backend
(5.8606e−03 against 1.4717e−05). That is consistent with the printed-input
rounding of §7.3 dominating this residual rather than with an implementation
error, although it is not by itself proof of that attribution — the two oracles
also sample different regions. The ±0.5 index sensitivity remains unquantified.

### 7.3 Why the official grid cannot be an accuracy oracle

| Input | Printed format | Recoverable resolution |
|---|---|---|
| `F10`, `F10B`, `S10`, `S10B`, `M10`, `M10B`, `Y10`, `Y10B` | `F8.0` (whole numbers) although `SOLFSMY` reads `F6.1` | ± 0.5 index |
| `SUN(1)`, `SUN(2)` | `F10.4`, radians | ± 5e−5 rad |
| `TEMP(1)`, `TEMP(2)` | `F8.1`, K | ± 0.05 K |
| `RHO` | `D15.5` | 5 significant digits |

The eight indices enter `TSUBC` with published coefficients of 0.178, 0.298,
0.312, 2.259 and 3.227 K per index unit (§5.4), so a ±0.5 index error is a
first-order error in the exospheric temperature. **The resulting density
uncertainty has deliberately not been quantified**: it would require either
measuring the density response to a ±0.5 index perturbation through this backend
at run time, or differentiating the model analytically. Neither has been done,
and no figure is asserted here. The bound is left explicitly unquantified.

The consequence is that a residual on this grid cannot distinguish an
implementation error from the fixture's own input rounding. The thresholds in
§7.4 are therefore chosen from the printed resolution, and the primary accuracy
claim rests on §7.1.

### 7.4 Official-grid thresholds — measured and calibrated

`tests/jb2008_tests.cpp` asserts, and the recorded run measured:

| Quantity | Threshold | Measured worst case | Margin |
|---|---|---|---|
| `RHO` relative, max | 1.5e−2 | 5.8606e−03 | 2.56× |
| `RHO` relative, RMS | 6.0e−3 | 3.2389e−03 | 1.85× |
| `TEMP(1)` absolute | 1.5 K | 0.75017 K | 2.00× |
| `TEMP(2)` absolute | 1.5 K | 0.74605 K | 2.01× |

The thresholds are therefore **calibrated against a measured residual**, with
roughly a two-fold margin on each. Their interpretation is narrower than the
numbers suggest: because the fixture's inputs are rounded to whole index units
(§7.3), the measured residual is dominated by that rounding and is *not* an
accuracy figure for the backend. The accuracy figure is the 1.4717e−05 of §7.1.

The thresholds stay **provisional for input rounding**: they cannot be tightened
to the accuracy the implementation actually achieves until the ±0.5 index
sensitivity of §7.3 is measured, at which point the residual floor of this
oracle becomes known and the gap between it and §7.1 can be attributed. No such
measurement exists, so none is claimed.

### 7.5 Other tests

`tests/jb2008_tests.cpp` additionally asserts: exact bit-reproducibility over
repeated evaluation; exact invariance under a right-ascension shift of the
evaluation point; invariance of the solar hour angle under a common
equator-origin shift of both right ascensions; `< 1e−12` relative invariance
under whole-turn right-ascension wrapping; `< 10 %` altitude-continuity over
120–600 km in 10 km steps; `DSTDTC` entering the exospheric temperature exactly
(`ΔTEMP(1) = ΔDSTDTC`); finite positive outputs for every official grid point;
the domain rejection table; the absence of constituent number densities; and the
IAU 1982 GMST standard used to rebuild the evaluation point from the fixture
grid.

The official archive is optional. Without `LEO_JB2008_VALIDATION_DIR` the fixture
cases report `SKIP` with the acquisition instructions rather than claiming a
pass. The variable may point either at the directory holding the `.DAT` files, or
at a parent containing `expected output/` or `jb-validation/`. The twelve
full-precision fixtures require no external data and always run.

## 8. Decisions

Append-only; superseded entries are retained. Dated 2026-10-10 unless stated.

**JB-D01 — Integrate the official Fortran; do not port the equations.**
*Question:* reimplement JB2008 in C++ or call the reference implementation?
*Options:* C++ port; external official Fortran.
*Selected:* external official Fortran, unmodified, hash-pinned, compiled in
place.
*Justification:* the requirement is a direct, uncached reference baseline; a
port would inevitably diverge in the 19/23-element `DTSUB` fits and in the
Newton–Cotes layer bookkeeping, and could not be validated against itself.
*Consequences:* a Fortran toolchain becomes a build dependency of the optional
component; the kernel stays free of it. *Limitations:* the operational driver
and its index files are not used. *Status:* final.

**JB-D02 — Never vendor the SET sources or data.**
*Question:* may `JB2008.f` or the validation output be committed?
*Selected:* no. Licence is "All rights reserved" with no grant of redistribution
or modification, so both stay outside the repository, are verified by SHA-256
and used read-only in place.
*Consequences:* the build cannot download; it requires an operator-supplied
path. The validation fixtures therefore cannot run in public CI, and the fixture
tests report `SKIP` rather than passing vacuously. *Status:* final.

**JB-D03 — Own the ABI bridge, own nothing else.**
*Selected:* `src/atmosphere/jb2008_bridge.f90` declares the reference call
inside an `ISO_C_BINDING` `bind(C)` wrapper. It contains no model equation, no
coefficient and no data. *Status:* final.

**JB-D04 — Serialise evaluation behind a mutex.**
*Question:* is `JB2008` reentrant?
*Measured by inspection:* it has no `COMMON`, `SAVE` or module state, so it is
reentrant.
*Selected:* still serialise. *Justification:* the read-me documents IEEE
underflow/denormal signals from the model; if a Fortran runtime were configured
to trap them, concurrent evaluation would make the signal non-deterministic.
Serialisation is free in the single-threaded propagation case. *Consequences:*
no in-library parallelism; wall-clock scaling is the caller's. *Status:* final.

**JB-D05 — Altitude datum is undefined by the source; keep the project's
ellipsoidal height as a documented engineering choice.**
*Question:* does `SAT(3)` have to be converted from geodetic height?
*Measured:* the distributed source does not state an altitude datum. The
6356.766 km in the gravity term is an effective-gravity fit constant and is not
the WGS-84 semi-major axis (6378.137 km), so it does not establish a reference
ellipsoid. The published grid is fed through untouched and therefore provides no
evidence either way.
*Selected:* pass the ellipsoidal (geodetic) altitude produced by the common
coordinate layer, which is the project engineering convention recorded in
`docs/atmosphere/DECISIONS.md`. *Justification:* the datum is not a requirement
of the model, so the project must choose one and document it; there is no
published basis in the distributed material for a different choice.
*Consequences:* if a primary publication defines the datum differently, this
entry must be superseded and the change quantified against that source.
*Limitations:* the magnitude of the difference between candidate datums has not
been measured against this model. *Status:* provisional, and explicitly *not* a
model requirement; the project engineering convention is unchanged and continues
to apply to the exponential atmosphere.

**JB-D06 — Use the reference index lags exactly (1/1/2/5 days).**
*Measured:* `SOLFSMY` is queried at `D1950 − 1, − 2, − 5` for F10/S10, M10 and
Y10 respectively, with the record index truncated, so the value is always the
previous calendar day's record and the 81-day centred averages are lagged with
it. *Selected:* exact. *Rejected:* NRLMSISE-00's F10/F81/ap timing, which is
unrelated. *Status:* final.

**JB-D07 — Sidereal argument is UTC, matching the reference driver.**
*Question:* should the hour angle use UT1?
*Measured:* `THETA` is evaluated from the UTC argument with no UT1 term, so the
driver treats UT1 as UTC. For 2023 |DUT1| stayed below 0.9 s, an hour-angle
discrepancy of at most 6.6e−5 rad.
*Selected:* the same convention on the validation path, so the published epochs
are reproducible. The propagation path obtains the actual Earth rotation angle
from SPICE Earth-orientation kernels; the two are therefore not identical and no
test asserts a numeric impact, because none has been measured.
*Consequences:* documented reproducibility difference; no claimed magnitude.
*Status:* final.

**JB-D08 — Reject rather than substitute missing indices.**
*Measured:* the reference driver replaces any index pair below 40 by zero and
then silently retries at the next input record, and aborts on `DST > 2000`.
*Selected:* `std::invalid_argument`. *Justification:* a requirement of this task
is that missing inputs fail clearly and are never silently replaced. *Status:*
final.

**JB-D09 — Primary oracle is the full-precision reference set; the official
rounded grid is a secondary structural check.**
*Question:* which oracle carries the accuracy claim?
*Rejected:* generating our own Fortran reference outputs — that is another
invocation of the same code and not an independent oracle; and transcribing the
model into another language, which the task forbids and which would produce
numbers with no independent provenance.
*Selected:* twelve full-precision reference densities (Orekit
`JB2008Test.java` @ `6fdf97c133c1ab8c56d7608688419bf4becacf80`, Apache-2.0) with
the upstream-inherited 2e−5 tolerance. Measured: max relative error
1.4717105248216975e−05, a 26 % margin. The official SET grid is retained
alongside because it covers 97 × 37 × 19 points per epoch and a wide `DSTDTC`
range, but its whole-number index printing (§7.3) prevents it from separating
implementation error from input rounding, so its thresholds are structural, not
accuracy, bounds.
*Measured:* full-precision oracle 1.4717105248216975e−05 against an inherited
2e−5 (26 % margin); official grid, 13328 samples, max 5.8605859224980525e−03, RMS
3.2388564212367911e−03, temperatures ≤ 0.75016676289965289 K. The grid residual is
398× larger than the full-precision residual on the same backend, which is
consistent with the printed-input rounding dominating it.
*Consequences:* the accuracy claim rests on a narrow altitude/latitude slice; the
structural claim rests on a wide grid whose residual floor is set by the
fixture's own input rounding. Neither oracle alone covers both, and the two
figures must not be compared as if they measured the same thing. Tightening §7.4
to the accuracy the implementation achieves requires measuring the ±0.5 index
sensitivity through this backend, which has not been done. *Status:* final for the
full-precision oracle; §7.4 calibrated against its measured residual but
provisional for input rounding.

**JB-D10 — Pin the compiler family, not just the model.**
*Measured:* the reference is fixed-form F77 with `IMPLICIT REAL*8`; a compiler
with a different default real kind or different legacy-Fortran handling would
change results silently. *Selected:* `cmake/jb2008.cmake` requires
`CMAKE_Fortran_COMPILER_ID STREQUAL "GNU"` and compiles with `-std=legacy`.
*Rejected:* claiming other compilers work unvalidated. *Status:* final.

## 9. Known limitations

* The accuracy claim rests on twelve full-precision fixtures covering
  MJD 53316.0 – 53321.5, 373–399 km and geocentric latitudes −52°…+74°
  (§7.1). Outside that slice the backend is exercised only against the
  rounded official grid, whose thresholds are structural rather than accuracy
  bounds (§7.4).
* The upstream origin of those twelve reference rows is undocumented: the
  Orekit test names no Fortran driver for them (§7.1).
* The official-grid residual is measured (5.8606e−03 max, 3.2389e−03 RMS over
  13328 samples, §7.2), but the ±0.5 index sensitivity is deliberately left
  unquantified (§7.3), so the residual floor of that oracle is still unknown and
  the §7.4 thresholds cannot be tightened to the accuracy actually achieved.
* Only 2023 DOY 91 is exercised against the official archive. Other epochs are
  supported by the model but were not validated, because no independent oracle
  is published for them in the freely distributable part of the archive.
* The altitude datum is not defined by the source (§4.4, JB-D05), and the
  sensitivity of the density to that choice has not been measured.
* The operational driver, `DTCMAKEDR_AUTO` and the `SOLFSMY`/`DTCFILE` readers
  are not linked. Input parsing and the hourly `DSTDTC` interpolation live in
  this project's weather layer and must reproduce §4.2/§4.3 exactly; that code
  is not part of this backend and is validated separately.
* The model provides no constituent number densities.
* The read-me warns that the model may signal IEEE underflow/denormal at high
  altitude; such signals are benign but would abort a Fortran runtime
  configured to trap them.
