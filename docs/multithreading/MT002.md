# MT-002: simple batch execution and process isolation

## Original problem and evidence

MT-001 established numerical correctness, not general parallel speedup. Its best measured parallel configurations reached **5.48× for J2**, but only **0.39× for full exponential**, **0.40× for NRLMSISE-00**, and **0.57× for JB2008**. The full-model numbers select different worker counts/batch sizes; they are not all eight-worker results. Six-hour confirmation also found full-model threading slower than sequential execution.

CSPICE uses a process-wide mutex; both non-reentrant native atmosphere implementations have their own process-wide locks. Representative eight-worker diagnostic runs recorded **39–44% contended SPICE acquisitions**. Exponential makes no native atmosphere call yet also slows down, so native-model serialization alone cannot explain the problem. Shared environmental/SPICE infrastructure is the leading supported bottleneck. Small adaptive RHS-count variation and small scheduling-policy differences do not explain the full slowdown.

These observations establish contention, **not a percentage attribution of production wall time**: diagnostic acquisition intervals include instrumentation/try-lock overhead and sum across threads, potentially exceeding elapsed time. Process isolation tests whether independent global library state improves end-to-end throughput without removing safety locks.

Eight-thread creation/readiness measured approximately **807 µs**, before release/join; this matters for short J2 batches. One worker remains the explicit inline default. See [MT-001 results](RESULTS.md) for the historical evidence, rather than repeating its matrices here.

## Thread versus process comparison

CASE-A, 64 deterministically perturbed trajectories, 1800 simulated seconds each,
30 s output cadence, seed `20261012`; unchanged `rtol=1e-10`, field absolute
tolerances and 15 s maximum step. Workers 1, 4 and 8; one warm-up and three
measured repetitions per configuration. Sequential means an explicit loop over
`propagate()`, not the inline batch path. Timing runs did not overlap builds or
validation.

The table reports median **wall seconds / trajectories per second / speedup**.
Parallel columns use eight workers. All worker counts and raw repetition times
are retained in [performance.json](mt002-evidence/performance.json), not another
large matrix.

| Workload | Sequential | Threads (8) | Processes (8) | Selected approach |
|---|---:|---:|---:|---|
| J2 | 0.1355 / 472.4 / 1.00× | 0.0795 / 805.4 / 1.70× | 0.1217 / 525.9 / 1.11× | Threads for sufficiently large batches |
| Exponential | 1.0328 / 62.0 / 1.00× | 2.7650 / 23.1 / 0.37× | 0.2722 / 235.1 / 3.79× | Application-level processes |
| NRLMSISE-00 | 4.5206 / 14.2 / 1.00× | 12.2967 / 5.2 / 0.37× | 0.8943 / 71.6 / 5.06× | Application-level processes |
| JB2008 | 6.2848 / 10.2 / 1.00× | 13.1036 / 4.9 / 0.48× | 1.1804 / 54.2 / 5.32× | Application-level processes |

Every route includes executable startup, independent kernel/weather loading,
propagation, binary output and atomic merge. The outer Python interpreter's
startup is excluded equally. This boundary differs from MT-001's solver-only
timings; speedups must not be compared directly across the two protocols. Even
the J2 control loads the same environment, making its short end-to-end result
startup-sensitive rather than a replacement for MT-001's solver scaling result.

Four and eight processes consistently beat sequential environmental propagation;
every environmental threaded parallel configuration loses. Process startup is
amortized for this environmental batch **as measured end to end**, not subtracted
or assumed free. J2 favors threads; eight processes are slower than four for J2.
One-process and inline results near 1× are not meaningful improvements.
All 112 runs, including warm-ups, compared complete binary outputs successfully.
The difference is large and consistent; no further performance sweeps were run.

Isolation improves throughput while retaining every lock. This strengthens the
shared-process-state explanation, but simultaneously isolates SPICE, native
models, existing exact-reuse state and allocator state: it does not assign the
wall-time loss to one mutex or rule out other shared-memory costs.

## Chosen architecture

```cpp
auto trajectories = leo::propagate_batch(
    factory, initial_states, epoch, sample_times, integration_options, 4);
```

One generic public function, one integer worker count, internal relaxed atomic
next-index assignment. `BatchOptions`, the public scheduling enum and static
partitioning are removed, with no aliases or compatibility API. One worker stays
inline; other counts are bounded by input size. Each trajectory owns its RHS,
stepper, adaptive state and output; results remain in input order. All trajectories
are attempted after trajectory errors, then the lowest failing input index and
original exception are reported after joins. `propagate()` is unchanged.
Historical policy differences are not compelling enough to retain two schedulers.

`mt_isolation` includes the existing experiment/benchmark source with its main
suppressed and reuses its scientific RHS, configuration and perturbation generator.
`process_batch.py` launches independent executables with explicit global input
ranges, then merges complete binary64 epoch, schedule and 13-component states in
input order. Every executable owns its provider, loaded kernels, weather data and
native globals; the Python parent never initializes those libraries. Locks remain
required inside each process. Failed execution/launch/merge preserves the prior
destination and reaps started children; empty, single and oversized batches are
supported. Empty batches use one executable to establish epoch/schedule metadata.

The route is deliberately concrete and outside `leo::integration`: no arbitrary
factory/lambda serialization, RPC, persistent process service or second public C++
batch API. Worker count defaults to one; execution strategy is explicitly selected
by the application, not silently changed based on the atmosphere model.

## Rejected alternatives and limits

- Removing CSPICE/native locks: unsafe for the current non-reentrant libraries.
- Generic process serialization/pools or a new abstraction hierarchy: unnecessary
  for the concrete experiment; would complicate ownership and error transport.
- Keeping static/dynamic policy selection: little full-model benefit, more public
  API and duplicate maintenance. Dynamic is a simple choice, not a universal optimum.
- Persistent workers, native context rewrites or shared stage-time preprocessing:
  architectural changes without a need to complete this phase.
- Density caching/interpolation or integrator/tolerance/model changes: out of scope.

One WSL2 Ryzen 7 5800H host, one representative batch size/case, warm filesystem
pages after warm-up, inherited eight-physical-core affinity, no per-worker pinning.
Three repetitions demonstrate the observed gap, not confidence intervals or
host-independent worker optima. Processes duplicate environment/data memory and
reload it on each batch; no child-memory scaling profile or cold-start claim.
The application route uses Python and the concrete executable's binary format,
not a general external process protocol. Broad Monte Carlo imbalance was not tested.

**Recommendation:** use in-process threads for gravity-only ensembles; use explicit
application-level processes for large SPICE-heavy batches; keep one inline worker
for generic full-model calls or short/small jobs where startup is not amortized.
Future work should start with a real repeated-batch application's memory/startup
requirements. Only then consider stable long-lived concrete workers or exact
shared environmental time-key preprocessing. Density caching remains deferred.

## Correctness and preservation

[correctness.json](mt002-evidence/correctness.json) records **24 passing six-hour
comparisons**: CASE-A, eight perturbed trajectories, all four workloads, threads
with four workers and processes with four/eight workers, two repetitions each.
Every epoch, all 721 sample labels and all 13 state components match the explicit
sequential reference byte for byte. No numeric tolerance is used for equality.

Six additional real-executable comparisons cover empty/single/three-trajectory
batches with 16 requested workers. Two simultaneously launched children use
different models, epochs and Ap configurations; distinct PIDs/epochs and complete
equality to separately executed references verify configuration independence.
The migrated thread validation executable passed ten short state/load/count
comparisons. Historical MT-001 stage/native-input and CASE-B/C evidence is reused:
the 49 existing physics/integrator/lock source files are unchanged.

The existing regression suite ran once: **184/184 passed** with the real
SPICE/native/weather fixture environment. The newly registered process contract
CTest passed separately, exercising seven Python cases with real child processes
for execution/partial-launch cleanup and malformed-output/publication boundaries.
A direct C++ batch smoke verified ordered results, complete binary64 agreement and
one-worker inline execution. No ThreadSanitizer or injected OS thread-launch
failure is claimed.

All **54 MT-001 evidence files**, **1608 historical evidence/tool files** and the
**49 existing core numerical/environment files** match their preservation hashes.
No frozen baseline, density cache/interpolation, scientific parameter, integrator
or lock cutover.

## Reproduction

Dependencies remain explicitly pre-acquired at the existing paths documented in
[PARAMETERS.md](PARAMETERS.md). GNU C/C++/Fortran 13.3.0, C++20,
`-O3 -DNDEBUG` (Fortran `-O3` and the existing JB2008 legacy flag), Eigen 3.4,
Boost 1.83, CSPICE N0067; no new dependency or fast-math flag. The small
[manifest](mt002-evidence/manifest.json) records source revisions, build/compiler
commands, hardware, dependency/input hashes and verification.
Implementation revision: `dd50666`; starting revision: `8a80653`. Measurements
precede final publication/input-contract hardening. Measured, six-hour-validation
and final-smoke executables have separate hashes in the manifest; physics is unchanged.

Use the configure command in [BENCHMARKS.md](BENCHMARKS.md), then:

```sh
cmake --build build-multithreading --parallel 4
for model in two_body_j2 exponential nrlmsise00 jb2008; do
  taskset -c 0,2,4,6,8,10,12,14 python3 docs/multithreading/process_batch.py \
    --binary build-multithreading/mt_isolation \
    --case docs/numerical-audit/experiments/CASE-A-v1.cfg --model "$model" \
    --total 64 --seed 20261012 --duration 1800 --cadence 30 \
    --benchmark --warmups 1 --repetitions 3 --report "/tmp/mt002-$model.json"
done
```

For application use, replace `--benchmark` with
`--executor processes --workers 8 --out /tmp/trajectories.bin`.
Choose `threads` for J2 or `sequential` for a single-process reference.
Extra scientific arguments following `--` are passed to the existing experiment
parser. The binary format is described by `mt_isolation --isolation-help`.
Do not target frozen evidence directories.
