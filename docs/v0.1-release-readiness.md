# v0.1 release-readiness report

Scope: pre-Python validation and benchmarking of the existing C++20 engine. No
pybind11 bindings, Python package, build backend, wheel or release is
implemented. NRLMSISE-00 and JB2008 are deferred to v0.2.0.

Source: `12d5cfb` (qualification work in `6e8b5df`, `f23c6cf`, `cf0e7f9`, `f20d1f0`).
Host: AMD Ryzen 7 5800H, 16 logical CPUs, Linux 6.18 WSL2, GCC 13.3.0 Release
`-O3 -DNDEBUG`, Python 3.12 / NumPy 2.5.3 / SciPy 1.18.1; separate pinned
Tudat environment `tudatpy 0.9.0`, native `tudat 2.14.0` (module `_version`
reports 0.8.0), Python 3.10, Boost 1.85.

## Verdict

**Numerically qualified for v0.1 within the stated limits.** All 17 scenarios
pass every frozen acceptance limit, against three independent oracles. One
genuine release-blocking input-validation defect was found and fixed. No
remaining issue blocks the v0.1 scope.

## Reference methods and versions

| Reference | Method | Independence |
|---|---|---|
| Analytical Kepler | Closed elliptic solution from the initial Cartesian orbit | No propagator |
| Analytical rigid body | Uniform spherical rotation; symmetric-top body rates | No propagator |
| SciPy DOP853 | 8th-order Dormand–Prince, tolerance ladder 1e-10/1e-12/1e-13, max step 30/10/2.5 s | Equations reimplemented; no LEO force function, header or integrator is called |
| Native Tudat | RKDP 8(7) higher-order fixed step, refined 5 → 2.5 s | Independent C++ astrodynamics toolbox; explicit mu, radius, normalized C20 |

Tudat required no kernel download: a constant zero-Earth ephemeris and a
zero-rate identity Earth rotation give the same fixed inertial +Z J2 axis with no
SPICE. Its `tudatpy.constants` module holds no Earth constants in this version,
so every Earth parameter is set explicitly. Python-module import worked only
after pinning `libboost=1.85` alongside Tudat, which is recorded rather than
worked around.

Reference-convergence margins are checked automatically before any engine
comparison: the final DOP853 refinement change must stay under 5 % of the
scenario's acceptance limit, or the scenario cannot serve as an oracle.

## Defect found and fixed

**Release-blocking input validation.** An `EarthEnvironment` constructed without
a Sun provider could be combined with enabled SRP/albedo and silently produced
plausible wrong loads (measured `a_x = 212.46 m/s²` from a Sun at Earth's
centre). Enabled drag with atmospheric acquisition disabled silently removed
drag instead of failing. Fix: `EnvironmentalDynamics` now cross-checks built-in
source/model compatibility at construction, and an explicitly zero Sun vector is
rejected at the SRP/albedo boundary. Three focused regressions cover missing Sun,
disabled acquisition, and intentional zero-density vacuum as a distinct valid
configuration. No valid-input force law, integrator, scheduler or default
changed.

The first full comparison also found CASE-B exceeding the frozen attitude/rate
limits at its initial 1e-11 / 5 s configuration (0.0118° against 0.01°). The
limits were **not** relaxed. Existing-solver refinement to 1e-12 / 2 s qualified
the scenario; an independent 1e-13 / 1 s confirmation showed the difference was
integration error, not a physical disagreement. The original failure is retained
in external evidence.

**Both Python alternatives are slower.** Native Tudat is 13–38× slower than the
C++ engine on matched gravity and rigid-body models; SciPy DOP853 is 140–1060×
slower. This is reported as measured. Tudat's large native advantage over SciPy
comes from its compiled RKDP 8(7) solver; SciPy DOP853 runs its stages and
controller in Python with only the NumPy vector algebra compiled.

Tudat rows for drag, albedo and the fully coupled cases are marked **Unmatched**:
its default atmosphere/panel/thermal/radiation equations are not the project's
flat-plate drag, cold-beam Sentman or radial-beam albedo definitions. No Tudat
default atmosphere is presented as an equivalent workload.

Those interpreter costs are measured around real children, not estimated, and
are excluded from the propagation ratios rather than silently folded in.

## Remaining limitations

1. **Fully coupled CASE-C at six hours remains numerically unresolved.** That is
   the pre-existing numerical-audit finding and this qualification does not close
   it. Only the shorter one-hour matched-environment horizon is qualified. Not a
   v0.1 blocker; the audit's conditional allowances stand unchanged.
2. **Matched-environment benchmarks are not SPICE contention measurements.** The
   scenarios use an explicit constant J2000 Sun and take no kernels. MT-002's
   real-environment result — environment-heavy threaded batches slower than
   sequential — is not superseded, extended or contradicted here.
3. **Memory comparison is partial.** Python peak RSS is a fresh-process figure
   including interpreter and imports; only logical retained `float64` output
   bytes are directly comparable. No C++ RSS or total-memory speedup is claimed.
4. **One host, one toolchain.** No cross-compiler or multi-host confirmation of
   the performance numbers.
5. **TudatPy version reporting is inconsistent** between distribution (0.9.0)
   and module metadata (0.8.0). Both identifiers are retained; neither was
   relabelled.

## Known performance bottlenecks

The bottleneck is per-step cost in the integrator loop, not setup, allocation or
I/O. C++ setup is ≤1.65 ms against multi-second six-hour propagations. The
Python gap is dominated by interpreted per-stage work: SciPy's DOP853 controller
and stages are Python. Within C++, the measured in-process batch scheduler scales
4.36–4.57× on 8 native workers for both a gravity-only and a fully coupled
workload, which is close to the observed per-trajectory-duration ceiling of this
16-logical-CPU WSL2 host.

No optimisation project was undertaken; none is warranted, and no correctness or
usability problem was found that would justify one.

## Release-blocking issues

None outstanding. The single blocker found (missing environmental data silently
producing plausible wrong loads) is fixed with focused regressions.

## Recommended next steps

1. Implement the bindings described in `docs/python-api-design.md`, with
   ownership, exception-translation and GIL tests as the first acceptance work.
2. Add a deliberate NRLMSISE-00/JB2008 exposure decision for v0.2.0, including
   whether optional acquisition belongs behind a Python environment object.
3. Re-run this qualification workflow after any change to `EarthDynamics`,
   force laws, the integrator or the batch scheduler.
4. Keep the frozen-fixture regeneration path explicit and off the ordinary CI
   path.

Measured and executed here: all 17 acceptance scenarios against three independent
oracles, 56 comparative benchmark configurations, batch determinism at four
worker counts, 119 C++ regressions, the frozen reference subset under GCC
ASan/UBSan, and a fresh-directory harness build. Reference generation and native
Tudat qualification were executed locally. Six-hour acceptance and comparative
performance are registered as a separately runnable manual workflow; that
workflow has not been executed on GitHub Actions, so the committed evidence is
